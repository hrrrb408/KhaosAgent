# Qwen3.8-27B CPU feasibility — Phase 0

- **Status:** PHASE_0_COMPLETE
- **Measurement date:** 2026-10-14
- **Repository baseline:** `95cad40cdf2540ffa409a5ec276d53720d6f9ce8` (`main` matched `origin/main`; existing untracked evidence was preserved)

## Result

Qwen3.8-27B Q4_K_M loaded and returned complete text actions in both the signed Khaos AgentHost at 8K and the standalone CPU runtime at 8K and 16K. The signed product smoke completed in 198.7 seconds. Four standalone runs completed in 184.7–198.8 seconds, with 15.42–17.29 prompt tokens/s and 5.46–6.21 generation tokens/s.

Peak sampled model-process RSS was 27.3–28.6 GiB. Swap did not grow during the runs. There were no crashes, OOMs, or timeouts. The outputs were complete and valid. These results establish a successful one-turn text path and stable 16K context configuration; they do not establish a multi-step coding task or a 16K-token-filled conversation.

The measured generation rate is close to the 5 tokens/s observation reference, and one simple product reply took about 3 minutes 19 seconds. A 6–8-decision task at this prompt/output size would take roughly 18–27 minutes of model time before approvals and Runner execution. Phase 1 will therefore remain a single bounded coding smoke; the 10–15 task benchmark is not started.

## Fixed measurement setup

- Input fixture: [`qwen38-phase0-user-prompt.txt`](fixtures/qwen38-phase0-user-prompt.txt), a synthetic request asking for one boundary case for `result = values[0].strip().lower()` and explicitly forbidding proposed or claimed tool execution.
- Standalone runs used the exact AgentHost system prompt and action grammar extracted from `khaos/macos/AgentHost.swift`, plus the same fixed request context. The prompt was 1,839 tokens and the completed response was 342 generated tokens in all four runs.
- Common arguments: 4 threads, `--device none`, `--ctx-size 8192` or `16384`, `--n-predict 32768`, `--temp 0.6`, seed 0, top-p 0.95, top-k 20, min-p 0, `--single-turn`, `--no-warmup`, `--offline`, and grammar-constrained JSON. The 32,768 token cap matches the existing AgentHost response cap; the model stopped after one short response.
- Every standalone invocation started a fresh process. The first and repeated runs distinguish first/repeat behavior, but the OS page cache was not controlled or directly measured. Model checksumming, signed-bundle packaging, and the product smoke had read the model before standalone testing, so none of these is a cold-disk measurement. The repeat runs are best described as process-cold with a likely warmer file cache.
- The configured 16K run used the same 1,839-token prompt; it tested a 16K context capacity setting, not a 16K-token-long history or context saturation.
- The pinned runtime's `load time` field is not a separate model-load measurement here. Source review shows `llama_perf_context_reset()` resets timing before prompt evaluation, and the first `llama_context::synchronize()` then overwrites `t_load_us` with elapsed time from that reset; accordingly it equals prompt-eval time. The table therefore uses wall time minus prompt+generation perf time only as an approximate pre-perf startup/load proxy. This proxy includes process, model, and CLI initialization and does not isolate weight loading.

## Decision and next step

- 8K and 16K context settings both completed stable standalone runs, produced full valid actions, stayed below the 600-second request deadline, and did not increase swap. The four generation rates averaged 5.87 tokens/s; prompt processing averaged 16.44 tokens/s.
- The observed rates are just above the initial 5 tokens/s reference, not a strong performance margin. The product turn took 198.7 seconds for one ordinary question. Assuming 6–8 decisions with similar prompt size, 342-token responses take about 18.5–26.5 minutes of model time. Shorter actions reduce generation time, while later requests have longer contexts; approvals and up to 180 seconds of Runner time are additional. This is a planning estimate, not an observed coding-task result.
- Phase 0 passes the load/stability/text-output gate for one bounded Phase 1 task, with high-latency risk recorded. Do not start the 10–15 task local benchmark before Phase 1 proves a complete read/edit/verify task and the user accepts the measured waiting time. Do not enable Metal in this phase.
- The initial product text request showed no tool proposal. This Phase 0 run did not test Action validity, tool-result continuation, scopes, or coding. The later Phase 1 smoke proved a read/edit/verify task and continuation after a nonzero test result, but did not capture raw Action JSON, correction counts, or a separate `can_continue=false` reply.

**Follow-up:** Phase 1 later passed its single read/edit/verify smoke, and the formal 12-task local/API baseline was then run. See [AgentHost compatibility](qwen38-agenthost-compatibility-2026-10-14.md) and [the updated comparison report](benchmark/dataset-v1/API_VS_LOCAL_RELIABILITY_2026-10-14.md). Those later results do not change these Phase 0 measurements.
